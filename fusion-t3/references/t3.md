# T3 Code transport for Fusion

Read this before the first dispatch. The operating policy lives in
`../SKILL.md`; T3 Code's orchestration tools are its transport. Where the
harness's own orchestration rules and this skill disagree, follow the
harness: it governs `delegate_task` mechanics everywhere, not only here.

## Before the first dispatch

Call `orchestrator_capabilities` once per thread, before the first
`delegate_task` — and again only after an error or a user-named provider
change. It tells you which providers and models can actually be delegated
to. Provider or model unavailable: say so. Never switch unasked, never fall
back to native subagents, Workflow, or CLIs.

Fusion's sidekick must be the operator's named cheaper model — usually
another provider, which is exactly what `delegate_task` is for. Collect the
operator's choices together once (provider, model, any settings beyond
yours); settings go in `target.options`. Record the approved `target` and
reuse it verbatim for every delegate. Never choose a model or provider the
operator hasn't named.

## Dispatch mechanics

- One `delegate_task` per handoff. Every review, rework and re-check is a
  new dispatch (brief, findings, objections) — **never** a `t3_thread_send`
  to continue a completed child.
- Each delegate's context is fresh and ends with the handoff: the brief is
  the whole task. Include the absolute path of `references/sidekick.md`
  with the operating instructions, name one report file per handoff, and
  point at earlier report/evidence paths for continuity.
- Follow the running delegate's `next`. Do not poll it — no `task_status`,
  sleep loops, watchers, Monitor, ScheduleWakeup. Wait so you wake once, on
  completion; every wake re-reads your context at your rate.
- Don't end the turn while a report is owed; never invent a pending result.
- Stop a delegate you replace or no longer need with `task_cancel` — never
  `t3_thread_interrupt` on a child thread. Cancel first, then dispatch the
  replacement; never two writers on one scope.
- Work in the project root by default. If a delegate needs a separate
  checkout, use the dispatch's own worktree isolation — never create a
  child's checkout in the shell or in `task`.

## Parallel delegates

Only genuinely independent, settled streams. Disjoint write scopes, no
checks colliding on the same artifacts, one brief and one report file each,
never more than 4 running at once (operator rule). Same approved target.
Told to run fewer: `task_cancel` the extras, start no replacements.

## Steering

A new user requirement mid-handoff: decide it changes the run, `task_cancel`
it, then one new `delegate_task` whose brief says what changed, what remains
valid, and to preserve completed work and live processes before finishing.
A safe handoff boundary beats a fast cancel: if the delegate is about to
land, let the result arrive and re-dispatch the delta.

## Authority stays with the lead

- Secrets: the lead calls `request_secret` and passes the `secretRef` to
  the delegate's tooling, or uses `delivery: "file"` for a shell command.
  Never ask in chat, never paste secret values into a brief.
- Commits, pushes, PRs, CI authority actions: lead only. Delegates never
  watch or babysit pull requests.
- Delegates never start subagents or workers; a child does its own work.

## Limits of this transport

Fresh delegates mean no shared conversation, no live in-flight steering
short of cancel-and-redispatch, and no usage/cost accounting. Continuity is
the filesystem: report files, evidence artifacts, and self-contained briefs.
Do not claim completion notifications, tool-policy enforcement, or measured
savings that none of these provide.
